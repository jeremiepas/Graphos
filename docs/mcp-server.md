# Graphos MCP Server

## Overview

The Graphos MCP (Model Context Protocol) server exposes code knowledge graph operations via JSON-RPC over stdio. It allows LLM agents and AI tools to query, explore, and build context from code graphs.

**Protocol**: MCP stdio (JSON-RPC 2.0, line-delimited)
**Version**: 2024-11-05
**Transport**: stdin/stdout — one JSON object per line

## Starting the Server

```bash
# From a pre-built graph.json
graphos --mcp graphos-out/graph.json

# Or programmatically in Haskell
startMCPServerFromFile "graphos-out/graph.json"
```

On startup, the server:
1. Loads the graph from disk (nodes, edges, communities, cohesion)
2. Loads chat history from `graphos-out/memory/` and enriches the community map
3. Runs analysis (god nodes, surprising connections, suggested questions)
4. Enters the JSON-RPC request loop on stdin

## Architecture: Chat History Community

Chat history is stored in a **synthetic community** added **after** Leiden detection:

```
1. LSP extracts code → Leiden community detection → pure code communities
2. Chat conversations loaded from graphos-out/memory/
3. enrichWithChatHistory adds community 0 = [conv_001, conv_002, ...]
4. Analysis runs on the enriched community map
5. select_context filters out community 0 by default (no pollution)
```

**Key design decisions**:
- Community 0 is reserved for chat history — never generated by Leiden
- Edges are **one-way**: conversation → code (code node degrees unchanged)
- `select_context` excludes community 0 by default; opt-in with `include_history=true`
- Chat nodes are `DocumentFile` type with `memory/` source prefix

```
Community 1: "Parser AST"          (Leiden)
Community 2: "Type Inference"      (Leiden)
Community 0: "Chat History"        (synthetic, post-detection)

Edges:
  conv_20260419 → Parser          (chat references code, one-way)
  conv_20260418 → TypeChecker     (chat references code, one-way)
  
  Parser ─/→ conv_20260419         (NO reverse edge — degree stays pure)
```

## Tools

### 1. `query_graph`

Query the knowledge graph using BFS or DFS traversal.

**Parameters**:
| Name | Type | Required | Default | Description |
|------|------|----------|---------|-------------|
| question | string | **yes** | — | The search question |
| mode | string | no | "bfs" | Traversal mode: "bfs" or "dfs" |
| budget | integer | no | 2000 | Token budget for results |

**Returns**:
```json
{
  "nodes": [...],
  "edges": [...],
  "traverse": [...] 
}
```

**Example**:
```json
{"name": "query_graph", "arguments": {"question": "authentication flow", "mode": "bfs"}}
```

### 2. `get_node`

Get details of a specific node by ID. Includes rich metadata from LSP extraction.

**Parameters**:
| Name | Type | Required | Description |
|------|------|----------|-------------|
| node_id | string | **yes** | Node ID to look up |

**Returns**: Node object with:
| Field | Type | Description |
|-------|------|-------------|
| id | string | Unique node identifier |
| label | string | Display name (function name, class name, etc.) |
| file_type | string | "code", "doc", "paper", "image", "video" |
| source_file | string | Source file path |
| source_location | string? | Start position (e.g. "L42") |
| line_end | int? | End line number (for exact code range) |
| kind | string? | Symbol kind: "Function", "Class", "Method", "Interface", "Constructor", "Variable", etc. |
| signature | string? | Type signature or declaration header |
| source_url | string? | URL to source (if available) |
| captured_at | string? | Timestamp when captured |
| author | string? | Author (if available) |
| contributor | string? | Contributor (if available) |

**Example**:
```json
{"name": "get_node", "arguments": {"node_id": "Auth.loginHandler"}}
```

**Response**:
```json
{
  "id": "12345_Auth_loginHandler",
  "label": "loginHandler",
  "file_type": "code",
  "source_file": "src/Auth.hs",
  "source_location": "L42",
  "line_end": 58,
  "kind": "Function",
  "signature": "Handler -> Request -> IO Response",
  "source_url": null,
  "captured_at": null,
  "author": null,
  "contributor": null
}
```

### 9. `select_context`

Select relevant context from the graph for an LLM query. Returns compact markdown with key nodes, edges, communities, and bridge nodes.

This is the core tool for **LLM context optimization**: a small LLM classifies the query complexity and selects the right subgraph strategy, then formats it as compact markdown for a big LLM's prompt.

**Parameters**:
| Name | Type | Required | Default | Description |
|------|------|----------|---------|-------------|
| question | string | **yes** | — | The query to select context for |
| budget | integer | no | 3000 | Token budget |
| include_history | boolean | no | false | Include past conversation history in context |
| verbose | boolean | no | false | Include per-node metadata (kind, signature, line range, community_id, degree, is_bridge) |

**How it works**:

1. Query classified by complexity: Focused / ModuleLevel / CrossModule / Architectural / Exploratory
2. Budget allocated based on complexity (higher complexity → more graph context)
3. Strategy selected:
   - **Focused/ModuleLevel** → Community-aware: find matching node → include its community + bridges
   - **CrossModule** → Path-based: shortest path between top 2 matches + neighbors
   - **Architectural** → God nodes + bridge nodes + community structure
   - **Exploratory** → Relevance-weighted BFS from matching nodes
4. Budget applied (max nodes, max edges)
5. Formatted as compact markdown

**Returns** (default mode):
```json
{
  "context": "## Relevant Code Graph (community-aware, 15 nodes, 25 edges, 1 communities)\n### Key Nodes\n- loginHandler [Function] [code] — src:src/Auth.hs:42-58 | Handler -> Request -> IO Response\n...",
  "complexity": "module",
  "nodes_selected": 15,
  "edges_selected": 25,
  "token_estimate": 1200,
  "include_history": false
}
```

**Returns** (verbose mode, `verbose=true`):
```json
{
  "context": "...(same compact markdown)...",
  "complexity": "module",
  "nodes_selected": 15,
  "edges_selected": 25,
  "token_estimate": 1200,
  "include_history": false,
  "node_metadata": [
    {
      "id": "12345_Auth_loginHandler",
      "kind": "Function",
      "signature": "Handler -> Request -> IO Response",
      "line_start": "L42",
      "line_end": 58,
      "community_id": 1,
      "degree": 5,
      "is_bridge": false
    },
    {
      "id": "12345_Auth_AuthMiddleware",
      "kind": "Class",
      "signature": null,
      "line_start": "L10",
      "line_end": 35,
      "community_id": 1,
      "degree": 12,
      "is_bridge": true
    }
  ]
}
```

**Verbose metadata fields**:
| Field | Type | Description |
|-------|------|-------------|
| kind | string? | LSP SymbolKind: "Function", "Class", "Method", "Interface", "Constructor", "Variable", "Module", etc. |
| signature | string? | Type signature (populated by LSP hover, currently null for most nodes) |
| line_start | string? | Start line (e.g. "L42") |
| line_end | int? | End line number — enables exact code range requests: `read_file("src/Auth.hs", 42, 58)` |
| community_id | int? | Which community this node belongs to |
| degree | int | Number of connected neighbors — high degree = important hub |
| is_bridge | bool | True if this node connects separate communities (high architectural importance) |

### 10. `add_conversation`

Store a conversation exchange for persistent cross-session memory. The conversation is saved to `graphos-out/memory/` and placed in the chat history community (community 0).

**Parameters**:
| Name | Type | Required | Default | Description |
|------|------|----------|---------|-------------|
| question | string | **yes** | — | The user's question |
| answer_summary | string | no | "(no summary)" | Short summary of the answer |
| source_nodes | string[] | no | [] | List of code node IDs referenced |

**Storage format** (YAML frontmatter + markdown):
```markdown
---
id: "conv_20260419T100000Z"
question: "How does authentication work?"
summary: "Uses JWT tokens with middleware chain"
timestamp: "2026-04-19T10:00:00Z"
relevant_nodes: ["Auth.loginHandler", "AuthMiddleware"]
tokens_used: 0
---
# Q: How does authentication work?

Uses JWT tokens with middleware chain
```

**Returns**:
```json
{
  "status": "saved",
  "conversation_id": "conv_20260419T100000Z",
  "question": "How does authentication work?",
  "linked_nodes": 2,
  "in_chat_community": false
}
```

Note: `in_chat_community` will be `true` on subsequent server starts (when conversations are loaded from disk and enrichment runs).

## Protocol Details

## Node Metadata

Every node in the graph carries metadata from LSP extraction:

### Compact format (in `select_context` output)
```
loginHandler [Function] [code] — src:src/Auth.hs:42-58 | Handler -> Request -> IO Response
```

### Symbol Kinds (from LSP)

| Kind | LSP Code | Description |
|------|----------|-------------|
| File | 1 | A file node |
| Module | 2 | A module or namespace |
| Class | 5 | A type class or class definition |
| Method | 6 | A method (class member) |
| Property | 7 | A property or field |
| Constructor | 9 | A data constructor |
| Enum | 10 | An enum type |
| Interface | 11 | An interface or type class |
| Function | 12 | A top-level function |
| Variable | 13 | A variable binding |
| Constant | 14 | A constant |
| Struct | 23 | A struct or record type |
| TypeParameter | 26 | A type parameter |

### Why Metadata Matters for LLMs

| Metadata | Token cost | Value | Use case |
|----------|-----------|-------|----------|
| `kind` | +1 | High | "Is this a function or a type?" — changes reasoning completely |
| `line_start` + `line_end` | +3 | High | Enables exact code snippet requests: `read_file("src/Auth.hs", 42, 58)` |
| `signature` | +5-10 | High | `loginHandler :: Handler -> Request -> IO Response` — understand without reading file |
| `community_id` | +1 | Medium | "This function belongs to the Parser community" |
| `degree` | +1 | Medium | "degree=12" = important hub node |
| `is_bridge` | +1 | Medium | "connects communities" = architectural cross-cutting concern |

### Protocol Details

### Request format
```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {"name": "get_node", "arguments": {"node_id": "Auth"}}}
```

### Initialize
```json
{"jsonrpc": "2.0", "id": 0, "method": "initialize"}
```
Returns server capabilities and tool list.

### Tool listing
```json
{"jsonrpc": "2.0", "id": 0, "method": "tools/list"}
```
Returns all 11 tool definitions with input schemas.

### Response format
```json
{"jsonrpc": "2.0", "id": 1, "result": {"content": [{"type": "text", "text": "{...json...}"}]}}
```

### Error format
```json
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32602, "message": "Missing required argument: node_id"}}
```

| Code | Meaning |
|------|---------|
| -32700 | Parse error (malformed JSON) |
| -32601 | Method not found |
| -32602 | Invalid params / missing arguments |

## Typical LLM Agent Workflow

```
1. User asks: "How does authentication work in this codebase?"
2. Agent calls select_context(question="how does authentication work")
3. Agent receives compact markdown context (~1500 tokens)
4. Agent includes context in prompt to big LLM
5. Big LLM generates answer using graph context
6. Agent calls add_conversation(question, summary, source_nodes) to persist memory
7. Next session: conversation_history finds relevant past exchanges
```
