## Context

Graphos scaffolds agent/skill files via `UseCase.Scaffold` (`src/Graphos/UseCase/Scaffold.hs`). `targetFiles` writes, per target:
- `opencode`: `.opencode/skills/graphos/SKILL.md` + `.opencode/agent/graphos-navigator.md`
- `claude`: `.claude/skills/graphos/SKILL.md` + `.claude/agents/graphos-navigator.md`
- `generic`: `.agents/graphos.md`

The current prose templates (`opencodeNavigatorProse`, `claudeNavigatorProse`, `opencodeSkillProse`, `claudeSkillProse`, `genericProse`) tell the model to run `graphos query`, `graphos path`, etc., and the navigator frontmatter correctly restricts bash to `graphos *`. But the prose does not explicitly frame `graphos` as the agent's toolset, does not name `graphos-out/` as the output directory, and does not warn against the unrelated `graphify` Python tool or `graphos_*` MCP tools. Two real-world misdirections exist in this repo:

1. `.opencode/agent/explore_graphos.md` — a hand-authored (no `generated by graphos` stamp) agent that instructs the model to call `graphos_query_graph`, `graphos_get_node`, … `graphos_conversation_history` (10 MCP tools). None of these are registered in this environment (the system prompt's tool list has `bash`, `read`, `grep`, `glob`, etc., but no `graphos_*` MCP tools). An agent following it fails.
2. `~/.claude/skills/graphify/SKILL.md` — a global skill for a different Python tool (`graphifyy` package) that writes to `graphify-out/` and shells out via `$(cat graphify-out/.graphify_python)`. It is listed in the system prompt's available skills and shadows the repo-local Graphos skill by name similarity.

The user-visible symptom: the agent tries to open the graph with Python or calls `graphos_*` MCP tools, instead of running the `graphos` CLI.

## Goals / Non-Goals

**Goals:**
- Make the scaffolded `graphos-navigator` agent and `graphos` skill unambiguously declare the `graphos` CLI as the toolset, name `graphos-out/` as the output dir, and warn against Python/`graphify`/MCP.
- Remove the stale `.opencode/agent/explore_graphos.md` (MCP-tool misdirection).
- Regenerate the repo's scaffolded files so they reflect the new prose.
- Keep the scaffold's idempotent-non-destructive contract for user-authored files.

**Non-Goals:**
- Modifying or removing the global `~/.claude/skills/graphify/` skill (outside the repo; different tool).
- Registering `graphos_*` MCP tools in the environment (out of scope; the MCP server exists but is not wired into this assistant's tool list).
- Auto-deleting user-authored agent files from the scaffold (violates the non-destructive rule; the `explore_graphos.md` deletion is a one-time manual cleanup).
- Changing the `graphos` CLI parser or the scaffold's target-detection logic.

## Decisions

### Decision 1: Declare `graphos` CLI as the toolset in the prose templates

Update the five prose templates in `Scaffold.hs` to add:
- A "## Your tool: the `graphos` CLI" section in the skill prose naming the `graphos` binary, listing the subcommands, and naming `graphos-out/graph.json` as the graph location.
- A "## Your tools" section in the navigator prose listing the `graphos` subcommands as the agent's tools.
- An explicit guardrail line: "Use the `graphos` CLI exclusively. Do NOT use Python. Do NOT use the unrelated `graphify` tool (it writes to `graphify-out/` and is a different tool). Do NOT call `graphos_*` MCP tools — they are not registered in this environment."

- Alternatives considered:
  - **A) Add a `tools:` frontmatter list of `graphos` subcommands** — rejected: opencode/claude frontmatter `permissions.bash.allow: [graphos *]` already covers the shell scope; a `tools:` list is not a standard frontmatter field for these assistants and could be misparsed.
  - **B) Generate a separate `TOOLS.md` listing the subcommands** — rejected: adds a file the assistant does not auto-discover; the skill/agent prose is the right place.
  - **C) Only warn against `graphify`, not MCP** — rejected: the actual observed failure is MCP-tool calls (`explore_graphos.md`), so the guardrail must cover both.
- **Selected**: prose sections in the existing templates. Minimal, no schema change, the model reads prose.

### Decision 2: Regenerate the repo's scaffolded files by deleting + re-running `graphos init --agents`

The scaffold's idempotent-non-destructive rule (`agent-scaffolding` spec: "Scaffolding MUST never overwrite an existing file") means `graphos init --agents opencode` will SKIP the existing `.opencode/skills/graphos/SKILL.md` and `.opencode/agent/graphos-navigator.md` because they already exist. To get the new prose in place, this change will:
1. Delete the two existing scaffolded files in this repo.
2. Run `graphos init --agents opencode` to regenerate them from the updated templates.

No `--force` flag is added to the CLI (keeping the non-destructive contract intact). The delete-then-regenerate is a one-time action performed as part of this change, not a recurring scaffold behavior.

- Alternatives considered:
  - **A) Add a `--force` flag to `graphos init --agents`** — rejected: weakens the non-destructive contract; the spec explicitly says scaffolding must never overwrite. A `--force` flag would need its own spec change and risks users clobbering hand-edited scaffolds. The delete-then-regenerate achieves the same end without a CLI change.
  - **B) Leave the existing files and rely on the prose change taking effect on next `graphos init` in fresh dirs** — rejected: the user's symptom is in THIS repo now; leaving the stale files means the fix does not take effect here.
  - **C) Manually edit the two existing files to match the new prose** — rejected: they carry the `generated by graphos 0.1.0.0` stamp; hand-editing them makes them diverge from the template and the next `graphos init` would skip them (stale forever). Regenerating from the template keeps them in sync with future template changes.
- **Selected**: delete the two existing scaffolded files, then `graphos init --agents opencode` regenerates them. No CLI change.

### Decision 3: Delete `.opencode/agent/explore_graphos.md` as a one-time cleanup

The file is not produced by `Scaffold.hs` (no stamp, not in `targetFiles`), references unregistered MCP tools, and misdirects the model. Delete it as part of this change. Do NOT add auto-deletion logic to the scaffold (that would violate the non-destructive rule for user-authored content).

- Alternatives considered:
  - **A) Keep it but add a "deprecated" header** — rejected: the model still reads the body and tries the MCP tools; a header does not prevent the misdirection.
  - **B) Move it to `.opencode/agent/explore_graphos.md.disabled`** — rejected: leaves clutter; a clean delete is simpler and the file is not user content (it contradicts the scaffold).
  - **C) Re-author it to use the `graphos` CLI instead of MCP** — rejected: it would duplicate `graphos-navigator.md`; the navigator is the canonical Graphos agent. If an MCP-mode agent is wanted later, a separate change can re-introduce it once MCP tools are actually registered.
- **Selected**: delete the file. If MCP tools are registered later, a separate change re-introduces an MCP agent.

### Decision 4: Rename the global `~/.claude/skills/graphify/` skill to `graphos`

The user wants the skill name to be `graphos`, not `graphify`. The global skill at `~/.claude/skills/graphify/` is the wrong-named one (it calls itself `graphify`, triggers `/graphify`, writes to `graphify-out/`). Rename it: `mv ~/.claude/skills/graphify ~/.claude/skills/graphos`; update `SKILL.md` `name:` frontmatter `graphify` → `graphos`; change the trigger `/graphify` → `/graphos`; replace `graphify-out/` → `graphos-out/` throughout `SKILL.md` and `references/*.md`. Update `~/.claude/CLAUDE.md` (the 3-line integration note) to reference `~/.claude/skills/graphos/SKILL.md` and `/graphos`. This is a user-environment file (outside the repo) and is touched as a one-time rename, not via the repo scaffold.

- Alternatives considered:
  - **A) Delete the global `graphify` skill entirely** — rejected: the user wants the skill named `graphos`, not removed; the skill content (retrieval playbook) is useful once the name is correct.
  - **B) Leave the global skill as `graphify` and only fix the repo-local skill** — rejected: the user explicitly asked for the name to be `graphos`; the global skill is the one that shadows the repo-local skill by name in the system prompt's available-skills list.
  - **C) Have the repo scaffold write to `~/.claude/skills/`** — rejected: the scaffold writes repo-local files (`.opencode/`, `.claude/` inside the repo); writing to the user's home directory is out of scope for the scaffold and would violate the architecture-purity boundary.
- **Selected**: one-time rename of the user-environment files, performed as part of this change's apply step (not via the scaffold). The repo scaffold continues to write only repo-local files.

### Decision 5: Update golden-file test fixtures

The `agent-scaffolding` spec has golden-file tests comparing scaffold output to fixtures. The new prose changes the golden output. Update the golden files in the same change so `cabal test` stays green.

- Alternatives considered:
  - **A) Add a separate test for the new prose without updating golden files** — rejected: the existing golden tests would fail; golden files must match the new output.
  - **B) Make the golden tests tolerant of the new section** — rejected: golden-file tests are exact by design; loosening them defeats their purpose.
- **Selected**: update the golden files alongside the template change. One atomic commit.

## Risks / Trade-offs

- [Deleting `explore_graphos.md` loses the MCP-mode retrieval playbook] → Mitigation: the playbook is preserved in git history; if MCP tools are registered later, it can be revived and adapted. The file is actively harmful now (calls non-existent tools).
- [The global `~/.claude/skills/graphify/` skill still shadows the repo-local Graphos skill by name] → Mitigation: this change renames it to `graphos` (Decision 4), eliminating the name collision. If other shadowing sources exist (shell alias, `graphify` binary on PATH), the next cycle addresses them.
- [Regenerated scaffold files overwrite any hand-edits the user made to the stamped files] → Mitigation: the existing files carry the `generated by graphos` stamp, signaling they are tool-owned; the spec's non-destructive rule protects user-authored files (no stamp), not tool-owned ones. The delete step targets only the two stamped files.
- [`cabal build` currently fails on `Extract/Core.hs:155`] → Mitigation: pre-existing unrelated parse error; this change does not touch that file. The build gate cannot run until it is resolved (note in tasks).

## Verification Strategy (Check)

- **Build gate**: `cabal build` zero warnings. Note: pre-existing `src/Graphos/UseCase/Extract/Core.hs:155` parse error blocks the build; it is unrelated and must be resolved separately for the gate to run.
- **Unit tests** (`cabal test`): the `agent-scaffolding` golden-file tests pass with the updated fixtures. The new prose sections ("Your tool: the `graphos` CLI", the guardrail line) appear in the golden output.
- **Manual acceptance**:
  1. After regenerating, open `.opencode/agent/graphos-navigator.md` — it lists `graphos` subcommands as the agent's tools, names `graphos-out/`, and warns against Python/`graphify`/MCP.
  2. Open `.opencode/skills/graphos/SKILL.md` — it has a "Tool: graphos CLI" section naming `graphos-out/graph.json` and the `graphify` warning.
  3. `ls .opencode/agent/` — `explore_graphos.md` is gone; `graphos-navigator.md` is the only Graphos-named agent.
  4. `grep -r "graphify\|graphos_query_graph\|MCP" .opencode/agent/graphos-navigator.md .opencode/skills/graphos/SKILL.md` — the only matches are the explicit "do not use" guardrail lines.
  5. `ls ~/.claude/skills/` — `graphos/` exists, `graphify/` does not; `head -5 ~/.claude/skills/graphos/SKILL.md` shows `name: graphos` and `/graphos`; `grep -r "graphify-out" ~/.claude/skills/graphos/` returns nothing.
  6. `cat ~/.claude/CLAUDE.md` — references `graphos` and `~/.claude/skills/graphos/SKILL.md`, not `graphify`.
- **Regression check**: the scaffold's idempotent-non-destructive behavior is unchanged (re-running `graphos init --agents opencode` after regeneration skips the existing files). Target auto-detection and the parser-derived command reference are unchanged.

## Iteration & Rollback (Act)

- **If Check fails** (e.g., a golden test reveals the prose change broke the command-reference rendering, or the regenerated file is missing a section):
  - Roll back the `Scaffold.hs` template changes and the golden-file updates; re-delete and re-regenerate the two scaffolded files from the old templates (or restore them from git).
  - File a follow-up PDCA cycle targeting the specific failure.
- **If the model still reaches for `graphify` after this change**, the next cycle checks for other shadowing sources (e.g., a shell alias, a `graphify` binary on PATH, a stale skill cache). The global skill rename (Decision 4) should eliminate the name collision; if it persists, the cause is elsewhere.
- **If the `Extract/Core.hs:155` parse error still blocks `cabal build`**, this change cannot reach its build gate — record as a prerequisite blocker in the task list and either fix it in a separate quick change or note it for the user.

## Migration Plan

- **Deploy**: (1) merge the `Scaffold.hs` template + golden-file changes; (2) delete `.opencode/agent/explore_graphos.md`; (3) delete `.opencode/skills/graphos/SKILL.md` and `.opencode/agent/graphos-navigator.md`; (4) run `cabal run graphos -- init --agents opencode` to regenerate them from the new templates; (5) `mv ~/.claude/skills/graphify ~/.claude/skills/graphos` and update `SKILL.md`/`references/` (`graphify` → `graphos`, `/graphify` → `/graphos`, `graphify-out/` → `graphos-out/`); (6) update `~/.claude/CLAUDE.md` to reference `graphos`.
- **Rollback**: `git revert` the template + golden changes; restore the deleted repo files from git; `mv ~/.claude/skills/graphos ~/.claude/skills/graphify` and revert the `SKILL.md`/`CLAUDE.md` edits.
- **User-facing change**: the Graphos agent/skill in this repo now explicitly names the `graphos` CLI and warns against `graphify`/MCP; the global skill is named `graphos` and triggers on `/graphos`. Document in the next CHANGELOG.
