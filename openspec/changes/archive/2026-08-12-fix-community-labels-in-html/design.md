## Context

Community labeling (PRD §5, `llm-labeling` spec) produces a `Map CommunityId Text` via `labelCommunities` (`UseCase/Label.hs`). The full pipeline (`Pipeline/Core.hs:241-254`) already calls it when `cfgLabel` is set and writes the result to `graph.json` via `IncrementalJSON.writeAnalysisTail` (the `community_labels` key). However:

- The HTML viewer is generated by `Infrastructure/Export/HTML.hs:exportHTML`, whose signature `Graph -> Analysis -> FilePath -> IO ()` carries no labels. `UseCase.Export.exportAll` (Export.hs:37) calls `epExportHTML ep g analysis hPath` and drops the `mLabels` it received. Inside `HTML.hs`, `communityAggregatesToJSON` (line 843) hardcodes `vcaLabel = T.pack ("Community " ++ show cid)`. So `graph.html` — which embeds its own copy of the aggregates, not `graph.json` — never shows LLM labels.
- `graphos ingest` has no `--label` flag (`ingestOpts`, Parser.hs:173). `runSingleFilePipeline` (Incremental.hs:189-197) passes `Nothing` to `epExportAll` and never calls `labelCommunities`. So even `graph.json` from an ingest run lacks `community_labels`.

The user-visible symptom: after `graphos ingest <file> --label`, the frontend shows `Community 3` instead of the LLM label.

## Goals / Non-Goals

**Goals:**
- Thread `Maybe (Map CommunityId Text)` from `exportAll` through `epExportHTML` into `communityAggregatesToJSON`, so the HTML viewer shows LLM labels (with a `"Community <id>"` fallback).
- Add `--label` to `graphos ingest`; invoke `labelCommunities` in `runSingleFilePipeline` when set; pass labels to `epExportAll`.
- Keep the `graph.json` schema unchanged (the `community_labels` key already exists).
- Preserve current behavior when labels are absent (no `--label`, or LLM unavailable): fallback to `"Community <id>"`, no crash.

**Non-Goals:**
- Re-architecting the `ExportPort` record beyond the one signature change.
- Changing the HTML viewer JS structure (it already reads `c.label` — the fix is in the Haskell that produces `c.label`).
- Persisting labels across incremental ingest runs (the index merge path is a separate concern).
- Re-clustering or re-labeling on every ingest (labeling runs once per ingest invocation, same as the full pipeline).

## Decisions

### Decision 1: Extend `epExportHTML` signature with a labels parameter

Change `epExportHTML :: Graph -> Analysis -> FilePath -> IO ()` to `epExportHTML :: Graph -> Analysis -> Maybe (Map CommunityId Text) -> FilePath -> IO ()`. Update `exportHTML` in `HTML.hs`, the wiring in `Wiring.hs`, and the call in `UseCase.Export.exportAll` (pass `mLabels`).

- Alternatives considered:
  - **A) Read labels back from `graph.json` inside `exportHTML`** — rejected: `exportHTML` runs before/alongside `graph.json` in some paths and re-reading couples HTML export to JSON file layout; also the incremental writer may still be open. Threading the in-memory `mLabels` is direct and pure.
  - **B) Stuff labels into `Analysis`** — rejected: `Analysis` is a Domain type (PRD §4.1) and labels are an export concern (they already live as a separate `Maybe (Map CommunityId Text)` argument to `epExportAll`); coupling them into `Analysis` pollutes the Domain layer.
  - **C) Make `community_labels` a field on `CommunityAggregate`** — rejected: `CommunityAggregate` is already the per-community record; adding an optional label field there duplicates the existing `community_labels` map and complicates the JSON shape.
- **Selected**: extend the port signature, mirroring how `epExportAll` already takes `Maybe (Map CommunityId Text)`. Minimal, consistent with the existing pattern.

### Decision 2: Use label-with-fallback in `communityAggregatesToJSON`

`communityAggregatesToJSON` gains a `Maybe (Map CommunityId Text)` argument. For each community `cid`, `vcaLabel = maybe ("Community " ++ show cid) id (mLabels >>= Map.lookup cid)`. The same label is also used in the overview dot `title` (currently `Community <id>: <N> members...`).

- Alternatives considered:
  - **A) Omit the fallback, leave `label` empty when no LLM label** — rejected: the viewer JS already renders `c.label`; an empty string breaks the sidebar list. The `"Community <id>"` fallback preserves the current UX when labeling is off.
  - **B) Always compute `suggestCommunityLabels` as a fallback inside HTML export** — rejected: `suggestCommunityLabels` (Domain.Community.Label) produces heuristic labels from member node names, not LLM labels; mixing them in the HTML path diverges from `graph.json` (which only carries LLM labels). Keep the HTML path identical to the JSON path: LLM label when provided, `"Community <id>"` otherwise.
- **Selected**: explicit LLM-or-fallback, matching the `graph.json` `community_labels` semantics.

### Decision 3: `--label` on ingest mirrors the full pipeline flag

Add `--label` (a `switch`, no argument) to `ingestOpts`, exactly like the full pipeline's `--label` (Parser.hs:56). The `IngestCmd` constructor gains a `Bool` for the flag. In `app/Main.hs`, the `IngestCmd` handler sets `cfgLabel` on the `PipelineConfig`. `runSingleFilePipeline` checks `cfgLabel` and, when set, calls `labelCommunities appEnv enrichedGraph finalCommMap Map.empty lblCfg` (cohesion is `Map.empty` here, matching the ingest path which doesn't compute it), then passes `Just labels` to `epExportAll`.

- Alternatives considered:
  - **A) Reuse `cfgLabel` from `graphos.yaml` only (no flag)** — rejected: the full pipeline has the flag; ingest should too for parity and for overriding config per-run.
  - **B) Add a `--no-label` flag instead** — rejected: default-off matches the full pipeline; adding `--no-label` would imply labeling is on by default for ingest, which it is not.
  - **C) Pass cohesion from `clusterSingle`** — rejected: `clusterSingle` returns `(CommunityMap, CohesionMap)` but the current ingest path discards cohesion (`_cohesion`); labeling's prompt uses cohesion but tolerates an empty map. Keeping `Map.empty` matches the existing ingest code and avoids a behavior change in clustering.
- **Selected**: `--label` switch on ingest, mirroring the full pipeline; thread into `cfgLabel`.

### Decision 4: LLM failure during ingest `--label` is non-fatal

If `labelCommunities` returns an empty label map (LLM error, parse failure, endpoint unreachable — `Label.hs:57-59` already logs and returns `Map.empty`), `runSingleFilePipeline` SHALL pass `Nothing` (or the empty map, treated as "no labels") to `epExportAll` and continue. The ingest succeeds; the HTML falls back to `"Community <id>"`. This matches the full pipeline's behavior (`Pipeline/Core.hs:250-254` calls `labelCommunities` and uses whatever it returns, including empty).

- Alternatives considered:
  - **A) Fail the ingest if labeling fails** — rejected: labeling is a presentation enhancement, not a correctness requirement; failing would block ingestion of valid files because of an LLM outage.
  - **B) Retry the LLM call** — rejected: retry logic belongs in the LLM port, not the pipeline; out of scope for this fix.
- **Selected**: non-fatal, log and continue. Consistent with the full pipeline.

## Risks / Trade-offs

- [Port signature change ripples to other `epExportHTML` callers] → Mitigation: there is exactly one wiring site (`Wiring.hs:204`) and one UseCase call site (`Export.hs:37`); both are updated in the same change. A grep for `epExportHTML` confirms no other call sites.
- [Partial labeling (some communities labeled, others not)] → Mitigation: the per-community `Map.lookup` fallback handles it; communities without a label get `"Community <id>"`. Documented in the spec.
- [Ingest with `--label` is slower (LLM round-trip)] → Mitigation: opt-in flag; user who doesn't want it doesn't pass it. No default behavior change.
- [Stale labels after re-ingest] → Mitigation: out of scope (the index merge path is separate); each ingest re-runs labeling from scratch on the current communities, same as the full pipeline.
- [`cabal build` currently fails on `Extract/Core.hs:155`] → Mitigation: that is a pre-existing unrelated parse error; this change does not touch that file. The implementation tasks will verify `cabal build` passes after the fix is applied (and will not be blocked by the pre-existing error, which must be resolved separately).

## Verification Strategy (Check)

- **Build gate**: `cabal build` completes with zero warnings (`-Wall -Wcompat -Werror`). Note: a pre-existing parse error in `src/Graphos/UseCase/Extract/Core.hs:155` currently blocks the build; it is unrelated to this change and must be resolved (separately or as a prerequisite) before the build gate can run. The task list will call this out.
- **Unit tests** (`cabal test`):
  - `communityAggregatesToJSON` with `Just (Map.fromList [(4, "Authentication Module")])` produces an aggregate for community 4 with `vcaLabel = "Authentication Module"`.
  - `communityAggregatesToJSON` with `Nothing` produces an aggregate for community 7 with `vcaLabel = "Community 7"`.
  - `communityAggregatesToJSON` with `Just (Map.fromList [(4, "X")])` produces an aggregate for community 7 (not in the map) with `vcaLabel = "Community 7"` (fallback).
  - A stub `ExportPort` records that `epExportHTML` was called with the `mLabels` argument passed to `exportAll` (verifies threading).
- **Manual acceptance**:
  1. With a working LLM endpoint (e.g., local Ollama), run `cabal run graphos -- example/ --label`. Open `graphos-out/graph.html`; the sidebar community list shows LLM labels, not `Community <id>`.
  2. Run `cabal run graphos -- ingest <file> --label`. Open `graphos-out/graph.html`; same label appearance. Check `graphos-out/graph.json` has a `community_labels` key.
  3. Run `cabal run graphos -- example/` (no `--label`). Open `graph.html`; community list shows `Community <id>` (fallback, no regression).
  4. Run `cabal run graphos -- ingest <file>` (no `--label`). `graph.json` has no `community_labels` key; `graph.html` shows `Community <id>`.
- **Regression check**: the full pipeline's `graph.json` `community_labels` key is unchanged (still written by `IncrementalJSON.writeAnalysisTail`); only the HTML now also reflects it.

## Iteration & Rollback (Act)

- **If Check fails** (e.g., a test reveals `communityAggregatesToJSON` still hardcodes the label, or the port signature change breaks a downstream caller):
  - Roll back the touched files: `ExportPort.hs`, `HTML.hs`, `Wiring.hs`, `Export.hs`, `Parser.hs`, `Incremental.hs`, `Main.hs`, and the `Command` type definition. No `graph.json` schema change to undo.
  - File a follow-up PDCA cycle targeting the specific failure.
- **If the port signature change turns out to ripple further** (e.g., a test or another wiring uses `epExportHTML` directly), split the change: first a mechanical pass-through of `Nothing` everywhere, then the label-using change.
- **If the pre-existing `Extract/Core.hs:155` parse error still blocks `cabal build`**, this change cannot reach its build gate — record that as a prerequisite blocker in the task list and either fix it in a separate quick change or note it for the user.

## Migration Plan

- **Deploy**: rebuild via `cabal run graphos -- <path> [--label]` or `cabal run graphos -- ingest <file> [--label]`. Existing `graphos-out/` files are regenerated on the next run.
- **Rollback**: revert the touched files; `graph.html` reverts to the `"Community <id>"` fallback; `graph.json` is unaffected (the `community_labels` key was already optional).
- **User-facing change**: `graphos ingest` gains a `--label` flag; the HTML viewer shows LLM labels when present. Document in the next CHANGELOG.
